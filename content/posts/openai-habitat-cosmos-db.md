OpenAI 的产品都需要快速、可靠地读写数据，由存储平台 Habitat 提供支持。它面向 40 个地理区域的超过 10 亿用户，要在毫秒级作出响应。团队要同时应对快速增长、新用例，并继续提升可靠性、性能和产品开发效率。我们的工作顺序是先让它足以承载关键业务，再让它对全球用户足够快，然后提高大规模运维的效率。

本系列讲述 Habitat 如何从 Python 客户端库加数据库，演进成处理超过 500 PB 数据的全球分布式存储平台。[第一篇](https://openai.com/index/scaling-storage-one-billion-users-part-one/)讨论 Python 服务的演进与扩容。本篇聚焦底层的 Azure Cosmos DB，以及双方工程团队共同运营容器、让多租户在全球规模下保持可靠和低读延迟的做法。

## 如何让多租户在大规模下可靠运行

单租户让各产品团队维护自己的系统，故障影响小、归属清楚、负载隔离直接。团队增多之后，单独做容量规划和预留资源的成本也不断增长。多租户把资源交给更熟悉数据库的中心团队统一管理，却会遇到一个租户吃掉其他租户所需资源的「吵闹邻居」现象。

Habitat 从一个共享容器起步，后来为部分用例配置专用容器，最终又默认使用共享容器。今天它承载多种用例，尽可能采用 Cosmos DB 提供的基础机制，许多额外能力因此可以稍后再做。

## Azure Cosmos DB 容器基础

- 账户定义一组容器及其复制策略。
- 每个容器用每秒请求单位 RU/s 表示所配吞吐。
- 数据按指定的逻辑分区键分片。每种键有文档规定的存储和吞吐上限。
- Cosmos DB 把许多逻辑键放在较少的物理分区上。物理分区达到存储阈值，或容器需要更多分区承接吞吐时，就会拆分。

## 第一阶段：依赖 Cosmos DB 的内建机制

最开始，每个账户只用一个默认容器，让客户端负载直接进入，并依赖每个逻辑键规定的 10,000 RU/s 上限施加背压。实际遇到三个问题。

### 逻辑分区键上限

早期 API 让客户端自行选键。不同产品常选择相同的 `user_id` 或 `workspace_id`，因而共享同一逻辑键的限制，某个用户可用的总吞吐受到约束。迁移前的 Postgres 也曾被热门组织或热键的大量请求拖垮。团队曾用缓存并给缓存未命中加租约，防止成批请求同时打到数据库。

### 吵闹邻居

文档列的是逻辑键上限，执行限制的实际位置是物理分区。一个逻辑键可用的吞吐还得与分区里的所有其他键共享。结果是，某个边缘功能可能抢占物理分区，影响使用其他键的登录和注册流程。

### 容量较弱的分区

容器的预配吞吐大致均摊到物理分区。数据变多时，物理分区会拆分。如果容器总吞吐保持不变，每个分区的吞吐就会降低。对于存储量大、类似对象存储的负载，即使请求量稳定，单纯的数据增长也可能降低活跃负载可用的吞吐。

## 第二阶段：尝试专用容器

分开的容器有独立的物理分区，能隔离热点和分区键冲突。代价是设置容器及其独立容量规划，所以最初只为关键新用例设置。团队还写了脚本，根据物理分区数调整容器配置，减少弱分区问题。

已有的关键业务要迁移才能离开默认容器。为避免默认容器承载更多负荷，团队逐渐建议每个新服务或大功能都开独立容器。这避免了多次全站故障，把影响限制在具体产品或服务上，但运维成本随后暴露出来。

### 失去平稳的聚合增长

在共享容器中，单个用例从零升到每秒一百万次请求，未必大幅改变总使用量。在独立容器上，同样的增长可能相当于内部试用基线的一千倍。各团队需要在上线前预扩容，有时忘记后就得在事故协作中临时调配。隔离换来了更小的影响范围，也失去了混合负载对总需求的平滑作用。

### 容量规划

了解专用容器何时会增长，越来越依赖具体产品知识。控制平面能按历史趋势调高吞吐，但没有平滑的总需求，就几乎要所有产品团队都参与规划。团队之间投入程度不一，这个运作方式也难以扩展。

## 第三阶段：默认共享，并保留搬迁能力

随着组织扩大，我们回到多租户方案，与 Azure 团队共同解决早期的问题。

- **热键限流。** 优先限制最热的键，避免它独占物理分区。
- **服务质量分级。** 批量导入和抽取等离线请求优先被限制，为用户交互保留吞吐。
- **改进的无服务器模式。** 旧模式按存储量扩展，单个物理分区最多 5,000 RU/s，限制了请求单位消耗大的用例。Azure 团队把分区上限提高到 10,000 RU/s，并引入基于 RU 用量的拆分。团队因而不用再人工监控和扩容容器。

这些变化让产品团队可以减少前期和后续容量规划，并保有负载隔离。原文报告，在此之后数月的快速开发中，团队没再因容量配置或吵闹邻居发生事故。

## 共同运营提高可靠性

到如此规模时，许多负载在云服务商那里也是异常大的案例。最大 Cosmos DB 账户保存数十 PB 数据，处理超过每秒 2,000 万次查询。团队因此需要共同测试、仪表板、直接工程沟通和共同负责故障模式。

2024 年底，一个主区域停电。切换时才发现最大账户切换到备用区域可能需要数小时，双方此前都没以这一规模演练。约一个月后，回切又触发严重故障。网关模式客户端在只有部分物理分区移回时，就集中连接和发送请求，原区域网关承受不了。

双方分别完成事故调查和改进，但这两次事故也揭示了测试与运维上的合作缺口。现在双方共同监控从 Habitat 服务到底层物理存储的各层，使用与生产同等规模的非生产账户测试变更，协同迭代 SDK、设定容量标准，并让工程师可以直接互相呼叫。

联合工作还包括提高控制平面和网关扩展性、缓存元数据来保护元数据分区、通过连接池和复用减轻 Python 服务的连接压力，以及尽可能共置负载，用独立 VPC 隔离关键与离线流量。这样跨组织工作是稳定性的关键。

## 提升全球性能

我们的顺序是先可用、再提速、再降本。系统在 2025 年趋于稳定并扩展到全球后，延迟成了下一道限制。计算与存储常位于不同区域，不可避免地跨区访问。

延迟随请求处理地和数据存放地而变化。产品团队曾用客户端缓存、批处理、减少数据库读写，以及移出关键路径来应对。产品因此更复杂，迭代也更慢，与 Habitat 降低数据库使用门槛的目标相冲突。2026 年团队为占请求九成以上的读操作做了分层优化。

### 容量允许时，把数据放近用户

在多个 Azure 区域设置账户可以满足数据驻留要求，也能给没有硬性驻留要求的用户降低延迟。现实中不少地区没有足够的存储、供电或冷却能力来承接本地用户比例对应的数据量。团队有时要在为就近存储保留容量与为服务计算增加容量之间权衡。

### 广泛复制小而延迟敏感的数据

每次请求都要的身份验证元数据等用例对往返时间敏感。部分 Cosmos DB 账户复制到全部 40 个服务区域，另一些至少覆盖每洲一个区域。Habitat 为此提前建立了透明的数据搬迁和路由层，让数据集能在复制拓扑不同的账户之间迁移。复制范围仍受容量约束，只用于少数挑选的数据集。

### 用集成缓存处理其余读取

应用频繁读取设置和状态，其中少数常访问类型占流量很大比例。Habitat 在用户请求的处理位置附近部署 Valkey，用旁路缓存保存近期访问的对象及其关联。常见的 TTL 设置在命中率与新鲜度之间取舍：时间短，常常要回源；时间长，过时数据可能保留更久。

写入时主动让缓存失效，可以改善新鲜度，但要处理部分失败和跨区域复制竞争。TTL 能限制最长陈旧时间，仍有折中。Habitat 参考 Meta TAO 等系统，使用 Cosmos DB 的变化流来传播失效。消费者在更新发生后几秒内让各区域缓存中的旧值失效，下次读取不命中，便从底层取最新值来填充。

### 用 Rust 减少代理开销

团队用 Rust 重写 Habitat 服务，减少了原 Python 实现的开销。几项改动共同把全球读延迟中位数从约 120 毫秒降到约 10 毫秒。最慢请求仍可能因为未命中而跨区回源。下一步需要提高存储效率并把数据放得更接近实际读者。

## 扩展变更数据捕获

CDC 把数据库变化传播到下游。除了缓存失效，每秒数百万条捕获变化经由一百多个 Kafka 主题，还用于最终一致的二级索引、搬迁流水线、离线分析和实时产品功能。底层跨越数千个容器与数百万个分区。如果让产品团队自行配置，就要选账户、容器和地区，再扩展监听服务、Kafka 与消费者。平台把这些细节封装起来，让产品只注册希望在行变化时调用的函数。

控制平面确保目标容器都被监听，选择读取地区，并在多地数千个 worker 间分派工作。读取副本并降低变化流优先级，以保护延迟敏感的在线流量。团队还加强了 worker 生命周期和租约处理、隔离不同流的故障，并给配置和上线过程增加保护。永久失败进入死信队列，避免堵住后续消息。区域故障时切换读取地；SDK 的进度检查点在内存批处理，再定期刷新，减少成本。

## 展望

窄接口、服务扩容和优先处理紧迫问题，使小团队得以支撑快速成长的存储平台。团队首先保证关键流量可靠，其次优化全球读性能，最后提高运维效率。

面向下一个十亿用户，需要在更大规模解决数据复制。团队正在构建面向大体量 Habitat 数据的 EB 级内部在线存储，结合来自 Rockset 的 RocksDB Cloud 核心与基于 Raft 的复制。它使用和 Cosmos DB 相同的文档模型，通过计算与存储分离和物理复制降低闪存容量需求，相应接受较低的峰值 QPS。
