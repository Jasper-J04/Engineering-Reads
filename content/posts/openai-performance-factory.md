智能体参与开发的速度快得惊人，传统性能工程的做法已难以持续。为跟上这个节奏，我们构建了 Performance Factory。这个运行在云端的自治系统借助 Codex 和模型寻找、调查并修复性能回归，让我们能跟上产品路线图。

工程师为重复发生的工作定义流程，并为执行它们的 Codex 智能体编写指令。以回归工作流为例，性能告警会启动一个任务。一个智能体调查变慢的原因，将发现记到任务中，然后提出修复供工程师审核。部署后，另一个智能体接手，检查性能是否回到基线。从调查、编写修复到确认缓解，这条工作流覆盖了修复回归的整个过程。在三个多月里，它追踪了 1,700 多次调查，找到了 600 多起问题的根因，平均每天执行约 17 次自动调查。

本文介绍我们如何从使用 Codex 演变到构建 Performance Factory，首条工作流如何运行，以及我们在生产环境构建与运行智能体工作流时学到的经验。

## 从人工调查到自动工作流

在性能工作中逐渐扩大 Codex 的使用范围后，我们看到团队的工作方式发生了连续变化。我们希望其他服务团队在不同领域采用智能体工作流时，也能参考这个过程。

1. **Codex 之前。** 工程师手动看指标和日志、比对追踪记录、调试运行中的机器并阅读代码。调查耗时，要知道从哪下手往往需要熟悉服务，相关信号也容易被遗漏。对于 ChatGPT 首 token 延迟回归等反复出现的问题，我们开发了 CPU 和内存分配剖析工具，逐步积累了 30 多种性能工具。
2. **把 Codex 当作搭档。** 工程师可以问「这里为什么变慢了」，与它一起调查不熟悉的系统。Codex 搜索大型代码库、查找指标和追踪、梳理服务交互，并按需进行性能剖析。但工程师仍需选择工具并引导过程。更多人得以用较少的专业背景和时间完成困难的调查。
3. **把调查方法写成可复用的技能。** 我们把工作方式整理为共享的 `perf-forensics` 技能，告诉 Codex 哪些工具可用、何时使用，以及怎样从异常起始时间、受影响请求、发布和配置变动三个方向调查。用历史回归做评估并调整技能后，对于 ChatGPT 延迟或可用性下降等目标问题，输入告警即可在一个会话里获得诊断。
4. **工程师成了中转站。** 告警响起后，工程师常常只是选好技能，把告警贴给 Codex，再把调查结果贴回 Slack。
5. **调查自动化。** 我们把调查移到云端，让告警自动启动 Codex 并在 Slack 线程发表发现。工作流到回复为止，工程师仍要接手诊断、修复和上线后验证。告警堆多了，光是从线程里找出要跟进的问题也很费力。
6. **建立工厂。** Performance Factory 跟踪每个任务接下来需要做什么，在条件满足时分派智能体。任务携带状态与证据，可以在人和智能体之间交接，也能等审核或部署完成后恢复。回归流程始于告警、终于验证生产恢复。常见优化还可以变成定期工作流，一个工作流发现机会后，可以交给另一个工作流验证并实现。

### 可配置工作流的任务服务

工程师通过配置文件和 Markdown 提示词来定义工作流。配置声明状态、允许的转换和需要人参与的步骤，独立的提示词告诉智能体每一步要做什么。代码改动任务可以有一份配置和分别用于实现、审核的提示。每项工作都成为可在界面查看的任务，工程师能跟踪进度或分享给有更多上下文的同事。

### 分派工作的调度循环

调度循环定期检查哪些任务具备执行下一步的条件。它用当前状态对应的指令启动 Codex。智能体把进展写回任务，完成后推进到下一状态。

### 云端 Codex

任务需要在能访问工程工具的地方执行。内部 API 在 OpenAI 网络中的云环境启动 Codex，使它能访问仓库以及指标、日志、追踪、CPU 剖析和内存快照等观测工具。智能体使用独立服务身份，权限可限定，操作可归因。多个任务可以同时运行，无需工程师保持笔记本开机或手动管理云端开发机。

### 事件订阅

等待人或部署时，智能体无需一直运行。任务可以订阅 PR 审核评论、CI 失败等事件。匹配事件到来后任务重新就绪，调度循环再分派智能体接手。

## 首条工作流：从告警到恢复

回归工作流将任务分为待调查、根因已确定、已提出修复、已解决等阶段。配置的告警触发后，发现与状态保存在单个智能体的上下文之外。工程师可以在 Slack 或工作流界面跟进、补充信息和审查改动。部署修复之后，智能体验证性能是否回到原来的基线。

### 智能体寻找根因

调查先回答哪些指标变差、什么时候开始、影响哪些请求。告警通常在指标越过阈值后才发出，回归可能已经发生数小时。智能体回看数据确定实际起点，并比较请求群体：是类似请求本身慢了，还是原本就慢的请求占比增加了？两者指向不同原因。

有了时间和影响范围，它再查发布记录、功能开关和代码，核对变更何时作用到受影响的请求，并用日志或追踪检验代码是否能解释异常。

### 用独立复核挑战诊断

早期，一些智能体碰到首个看似合理的解释便停了。我们增加了单独的 Codex 会话来推翻候选诊断。它重查假设和反事实，例如未收到发布的类似请求是否仍健康、回退变更后异常指标有没有恢复。

有一次，调查将 ChatGPT 对话失败归因于下载图片出错。复核者发现，负责查找文件的内部服务已恢复，图片请求却还在失败。原解释讲不通持续失败的部分，复核者重新打开调查并记录还需要证实的内容。

对 100 个根因建议的人工抽查中，70% 判为准确，30% 需要继续打磨或证据还不足以确立因果。工作流将调查、质疑和提修复拆给不同会话，形成相互检查。

### 修复回归比找到原因更难

诊断通过复核后，Codex 实施修复并打开 PR。工程师决定是否合并。为便于交接，每项任务生成一份报告，列出回归、影响、根因和候选修复，并附指标时间序列、CPU 火焰图与追踪。工程师可以改 PR、根据诊断另写补丁，或发表评论唤醒智能体继续处理。

部署后恢复到基线，任务标为解决；部分恢复时，关闭原回归并为余下的问题单开任务；没有改善时，记录情况并退回调查。候选改动有时过于复杂，有时会引入新问题，因此每项修复也接受独立复核。比如增加缓存可能提速，也可能让读到的数据过旧，此时需要了解服务的工程师权衡。

我们正在比较智能体提出的修复和工程师最后合并的改动，把差异变成评估。团队也在尝试让智能体先用合成性能测试衡量并修订补丁，并研究怎样借助其他自动化审核工具识别低风险改动。

## 生产运行中学到的经验

### 保护工程师的注意力

原始的调查输出可能很长，工程师要从中提取主张，再找到支撑它的图表。我们希望人把注意力放在决策上。早期界面装满了调查结果，同一回归还可能从不同告警、监控和频道多次出现。现在工作流关联相关事件，按团队关注的指标分组，再估计影响并排序。工程师可以把时间留给补充上下文、权衡与决定发布内容。

### 分开评估调查和交接

改技能或升级模型后，有些病例可能变容易，有些会变差，因此我们分别测试调查能力和摘要对工程师的用处。

调查测试用真实历史事件回测。每个用例让一个全新的 Codex 调查者从去掉泄题线索的原始信号开始，并与当时的真实解决记录比较。指标和追踪会过期，事后证据又可能泄露答案，因此要明确智能体当时能看见什么。它可在限制内读代码和查生产遥测，但不读取备忘、事故复盘或之前的结果；结束后也会检查会话是否误接触了答案。起始时间、影响大小、请求范围、可能原因的证据和仍未确定之处分别评分。

摘要评估则用保存的任务快照回测，避免依赖会过期的外部指标。独立评分者看不熟悉系统的工程师能否理解发生了什么、为什么重要，关键图表是否保留，下一步建议是否有证据。

### 把重复失误变成自我修复

性能工具损坏或权限缺失，会让智能体无法核实原因，最终报告里却未必看得出来。我们每天让一个智能体检查近期运行消息和日志里的工具失败与访问错误。同一种错误阻塞多次调查时，它在工厂创建修复任务。原因明确时，另一个智能体提改动，由工程师决定是否合并。合并后用评估确认智能体能否通过原来卡住的步骤。

## 接下来：更多工作流与主动监测

回归流程是显式状态驱动的一例：有工作可做时智能体推进任务，独立复核挑战结论，需要判断时工程师参与。其他工作流可以复用机制，换用各自的状态、指令与事件。

现在回归工作流由告警启动。我们也在探索主动发现：利用不同版本间的 CPU 与内存剖析、堆转储和请求追踪，捕捉尚未触发告警的变化。比如发现某类请求的 CPU 使用略高时，智能体可以创建任务、追到根因、实现修复并打开 PR。

对于已经有判断方法的问题，我们把模式写入工作流。服务规格调整技能便可发现自动扩缩容保留了多余副本。把这样的工作定期放到各服务上运行，一个工程师从某次回归学到的经验，就能用来解决数月后另一个服务的问题。

下次用 ChatGPT 时感觉变慢，Performance Factory 可能已经在调查。现在的瓶颈可能是等待工程师审核并合并修复，我们也在探索何时能将这一步交给智能体。随着开发提速，性能系统也需要不断提高自治和自我改进能力。Codex 已经帮助我们更快地构建 ChatGPT，现在也在帮助我们让它保持快速。
